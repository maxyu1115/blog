> **TL;DR**
>
> - FBT feeds each position's final hidden state back into the next position, so theoretically the model's depth can grow linearly along the sequence length through a **latent chain**. We set out to investigate how effective this chain is.
> - FBT can learn a long chain. Trained on *Cups*{:.task}, a cup-swapping task, it tracks the ball through 65 to 128 swaps over 7 to 23 hops, against about 2 after [pretraining](#1-pretraining).
> - But it uses the chain only as a last resort. It would rather write the state in its CoT, and only a length penalty makes it rely on the chain.
> - We come up with two techniques for doing on-policy RL for FBTs (through multiple hops) that are significantly more efficient than naive methods ([section 2](#2-rl-on-fbt)).
{: .prompt-info }

The full-bandwidth transformer (FBT, [Wang et al., 2026](https://arxiv.org/abs/2608.08888)) makes one change to a decoder-only transformer. The top-layer hidden state of the previous position goes back into the bottom of the stack, next to the sampled token. We call each step through this feedback a **hop** ([section 0](#0-full-bandwidth-transformer-background)). 

FBT's hops scales linearly with the sequence length, but since it is pre-trained with a $K$-pass jacobi, we wonder how many effective hops FBT can actually utilize. This question becomes particularly interesting with RL, where if done properly, is trained with an exact $\|x\|$-hop latent chain rather than an approximation through $K$-pass jacobi (often $K\leq 3$).

We post-trained small FBTs with SFT and RL on five synthetic tasks that need state tracking, to see how they use this latent chain (sections [3](#3-exploring-fbt-on-synthetic-tasks) and [4](#4-findings)). In *Cups*{:.task}, for example, a ball hides under one of 5 cups that get swapped many times, and the model can track it by writing the cup in its CoT or by carrying it in its latents. These tasks favor the latent chain, so we read the results as an upper bound on how much FBT would rely on it in realistic tasks.

## 0. Full-Bandwidth Transformer Background

![FBT's latent feedback](/assets/img/fbt/arch-light.svg){: .light w="573" h="358" }
![FBT's latent feedback](/assets/img/fbt/arch-dark.svg){: .dark w="573" h="358" }
_**Figure 1.** FBT's latent feedback. Each position's top state is fused with the next token's embedding at the bottom of the stack (orange). The rest is a standard transformer (gray)._

FBT replaces the token embedding at layer 0 with a fusion of the token and the previous position's top state (Figure 1):

$$
u_t = \mathrm{fuse}(h_{t-1}, e_t) = \mathrm{norm}\big(\underbrace{W_H\, h_{t-1}}_{\text{value}} \odot \underbrace{\sigma(W_G\, e_t)}_{\text{gate}}\big), \qquad h_t = F_\theta(u_1, \dots, u_t),
$$

where $e_t$ is the token embedding, $h_{t-1}$ the previous position's top state, $F_\theta$ the causal stack of $L$ blocks with its final norm, and $W_H, W_G$ the only new weights. The value comes from the previous state, and the token only gates it.

The feedback also deepens the computation. In a standard transformer, layer $l$ sees earlier positions only through their keys and values at layer $l$, which the layers below computed. So nothing position $t$ computes is deeper than the $L$ layers of the stack, however long the sequence. In FBT, layer 1 of position $t$ reads $h_{t-1}$, which already drew on every layer of the earlier positions, so each hop can add another $L$ layers of depth (Figure 2). This helps with things like tracking a state internally across many tokens.

![What one layer can read](/assets/img/fbt/depth-light.svg){: .light w="573" h="320" }
![What one layer can read](/assets/img/fbt/depth-dark.svg){: .dark w="573" h="320" }
_**Figure 2.** What one cell, a layer at a position, can draw on. In a transformer, layer 3 sees earlier positions only through the layers below it. In FBT, even layer 1 reaches every layer of every earlier position, through the previous position's top state._

Decoding computes $h_{t-1}$ anyway, so there the feedback is nearly free. Done exactly, prefilling or pretraining on $T$ tokens would take $T$ serial forwards. To prefill and pretrain efficiently, FBT instead runs $K$ **Jacobi passes** over the whole sequence. Pass 1 is the plain GPT forward, and pass $k$ feeds each position the previous pass's state of the position before it:

$$
h^{(1)} = F_\theta(e), \qquad h^{(k)} = F_\theta\big(\mathrm{fuse}(S h^{(k-1)}, e)\big), \qquad (S h)_t = h_{t-1}.
$$

Pass $k$ is exact on the first $k$ positions and approximates the recurrence past them. We call one step of feedback, from position $t-1$ to $t$, a **hop**, so $K$ passes give at most $K-1$ hops. A hop counts one use of the feedback, not one position. Between hops, attention can move information across many later positions, so a chain of 20 hops can span hundreds of tokens. The loss averages the feedback passes, with gradients through all of them:

$$
\mathcal{L} = \mathcal{L}_1 + \frac{1}{K-1}\sum_{k=2}^{K} \mathcal{L}_k.
$$

Each pass costs a full forward and backward, so FBT trains with $K \le 3$, mostly $K = 1$. The paper's 1B schedule spends 75% of the steps at 1 pass, 22% at 2 and 3% at 3, which we write as 75/22/3. This rests on the passes converging fast, so that by $K = 2$ the states are mostly at their fixed point, the exact recurrence. How many hops a trained model actually uses is the question that runs through this post.

FBT belongs to a family of models that carry a hidden state from one position to the next. The Feedback Transformer ([Fan et al., 2020](https://arxiv.org/abs/2002.09402)) lets every layer attend to past positions' higher-layer states. Coconut ([Hao et al., 2024](https://arxiv.org/abs/2412.06769)) feeds the last hidden state back as the next input while reasoning. LRT ([Huang et al., 2026](https://arxiv.org/abs/2605.26797)) reuses a high layer's state from the previous token, and T2MLR ([Cai et al., 2026](https://arxiv.org/abs/2607.15178)) fuses a middle layer's state into an earlier layer.

## 1. Pretraining

We ported FBT into [nanochat](https://github.com/karpathy/nanochat)'s pretraining stack, starting from Xi Wang's own FBT reproduction on nanochat ([xidulu/Full-bandwidth-transformer](https://github.com/xidulu/Full-bandwidth-transformer)), and pretrained it from d6 to d14 (dN has N layers, 23M to 164M parameters) on ClimbMix ([Diao et al., 2025](https://arxiv.org/abs/2504.13161)). At our scale we couldn't fully reproduce the paper's language modeling gain. With the paper's 75/22/3 schedule, the second pass never beats the plain pass. With 66/28/6, which spends more steps on feedback, it does from d10 up, so every model we fine-tune is pretrained with 66/28/6. [Appendix B](#appendix-b-reproducing-fbt-pretraining) has the setup, how it differs from the paper's, and how FBT compares with GPT.

**The pretrained chain is short.** Each pass changes the state about 10 times less than the last (Figure 3).

![Change per pass on text](/assets/img/fbt/delta_text-light.svg){: .light w="632" h="340" }
![Change per pass on text](/assets/img/fbt/delta_text-dark.svg){: .dark w="632" h="340" }
_**Figure 3.** Each Jacobi pass changes the state about 10× less than the last. $\Delta_k$ is the RMS change of the normed top state from pass $k-1$ to $k$, on 2M validation tokens, for pretrained FBTs from d6 to d14 (66/28/6, the share of steps at 1, 2 and 3 passes). By pass 5, the validation loss in bits per byte (bpb) is within 10⁻⁶ of its 16-pass value._

On text, a change at one position is mostly gone two positions later, so the pretrained chain is about two hops long and the third pass adds nothing. This is where fine-tuning starts in [section 3](#3-exploring-fbt-on-synthetic-tasks).

## 2. RL on FBT

For a standard transformer, RL samples rollouts, scores them, and computes the gradients from one forward over each rollout, which reproduces the sampler's log-probabilities at each position.

FBT samples token by token, carrying each position's latent to the next. Its usual training forward instead approximates that recurrence with a few parallel Jacobi passes, which is off policy to the rollout.

So the rollout has to save the latents along with the text. And since each latent was computed by the position before, the gradient should ideally reach back across positions through the latents. Two techniques handle this.

### 2.1. Replaying the sampler's latents

The sampler saves the latent it fed each position, $z_t$, and the trainer replays the rollout in one forward with every position fed its saved latent:

$$
h = F_\theta\big(\mathrm{fuse}(z, e)\big).
$$

Replay matters in two places:

1. **The policy gradient.** The trainer recomputes the trajectory's log-probabilities to differentiate them, and they are on policy only if every position is fed the latent it was sampled with.
2. **Re-prefilling.** When a sequence's KV cache is evicted or expires mid-rollout, the sampler recomputes it before continuing. Recomputing it from its tokens alone would give it different latents from the ones its tokens were sampled with, so the sampler feeds the saved ones back in.

Without replay, the natural substitute is a $K$-pass Jacobi forward over the rollout. It matches the sampler only on the first $K$ positions, so past them its log-probabilities, and the gradients computed from them, are off policy. The mismatch is large once a model leans on a long chain. [Huang et al. (2026)](https://arxiv.org/abs/2605.26797) measured what staying on policy is worth for LRT (a similar architecture). On GSM8K with GRPO, starting the RL forward from the rollout's cached states, instead of recomputing them with parallel refinement passes, raised pass@1 from 12% to 14% and pass@16 from 41% to 50%.

### 2.2. Gradient through H hops, from one forward

Replay alone leaves $z$ a constant. The loss at position $t$ can't send gradient back through $z_t$ into position $t-1$'s computation, so the model learns to read its latents but not to write latents that help later positions.

To send the gradient back $H$ hops and stay on policy, we can run $H+1$ Jacobi passes **pinned** to the rollout. In pass $j$, position $t$ is fed

$$
z_t + \big(h^{(j-1)}_{t-1} - \operatorname{sg}(h^{(j-1)}_{t-1})\big),
$$

where sg is a stop-gradient. The value is always the saved $z_t$, so every pass matches the sampler, while the gradient flows into the previous pass's state at position $t-1$, one hop further back per pass. Similar to the concurrent KL gradient-recovery trick of [Teoh (2026)](https://arxiv.org/abs/2610.38331), the added term is numerically zero and only routes the gradient.

Run literally, that is $H+1$ forwards and $H+1$ passes of activations. But every pinned pass computes exactly the same values, since each is fed the same $z$. So the forward only needs to run once, and only the backward is repeated (credit to Claude, which came up with this trick). Each repeat is a backward to the fed latents alone, through the one forward's graph, and a shift back one position, which carries the gradient one hop further. The weights then need a single full backward, with the gradient summed over the hops ([Appendix C](#appendix-c-deriving-the-gradient-trick) derives it):

```python
hidden = stack(inputs_embeds, token_embeds, z)  # z: saved latents
total = g                                       # dL/dh
for _ in range(H):
    # one hop: back to the fed latents, then back one position
    (g,) = torch.autograd.grad(hidden, z, g, retain_graph=True)
    g = torch.where(chained, g, 0).roll(-1, dims=1)
    total += g
torch.autograd.backward(hidden, total)  # one backward into the weights
```

(`chained` masks out positions that weren't fed a latent, such as a document's first token.)

So the gradient is that of $H+1$ pinned passes, but the forward runs once, and what grows with $H$ is only the number of backwards to the latents. Table 1 compares the options.

**Table 1.** The cost of one RL step on FBT, relative to a standard transformer's step (one forward and one backward). Gradient hops is how far back through the latents the gradient reaches. Compute counts a forward as 1/3, a full backward as 2/3, and a backward to the latents alone, which skips the weights, as about 1/3. Memory is the stored activations, which grow with the rollout's length $T$ in every row.
{: .caption}

| training step | on policy | gradient hops | compute | memory |
|---|---|---|---|---|
| standard transformer<br>(the unit) | yes | | 1 | 1 |
| $K$ Jacobi passes | first $K$ tokens | $K-1$ | $K$ | $K$ |
| replay | yes | 0 | 1 | 1 |
| $H+1$ pinned passes | yes | $H$ | $H+1$ | $H+1$ |
| replay + $H$ hops<br>gradient trick | yes | $H$ | $\approx 1 + H/3$ | 1 |

$H$ only sets how far back the gradient reaches in training. It doesn't cap how many hops the model uses, which we measure separately ([section 3](#3-exploring-fbt-on-synthetic-tasks)). [Section 4.4](#44-long-chains-reach-further-with-a-gradient-through-the-latents) compares $H$ = 0, 2 and 8.

## 3. Exploring FBT on Synthetic Tasks

We fine-tune FBT on five synthetic tasks and ask whether it computes through its latents, and over how many hops.

- *Cups*{:.task} hides a ball under one of 5 cups and swaps the cups around. The answer is the ball's last cup. The completion first restates each swap and may write the ball's cup after it.
- *Dataflow*{:.task} is a program that updates 4 registers mod 100. The answer is their last values.
- *Turtle*{:.task} moves a turtle around a 10 × 10 torus by turning or stepping forward. The answer is its last position.
- *Calendar*{:.task} shifts a date by up to 28 days at a time, either way. The answer is the last date.
- *Arithmetic*{:.task} evaluates an expression mod 100 with +, − and ×, one operator per line.

{% include fbt/task-examples.html %}
**Figure 4.** One example chat per task, much shorter than those we test on. The completion restates the prompt one step per line and may write the state after a step (highlighted).
{: .caption}

In every task, each line of the completion restates one step and may end with the state after it, like `25>2` in *Cups*{:.task} (Figure 4). When it does, we say the completion **writes the state**, using the CoT to track it. In the SFT data a random share of the lines write it, so RL is free to choose how much to write. *Arithmetic*{:.task} writes the whole state on every line. What it can leave out is steps, since in the runs with the length penalty its SFT data also has lines that evaluate two or three operators at once.

We rate each task on two kinds of difficulty. **Tracking difficulty** is how hard it is to follow the state across many updates, and **step difficulty** is how hard one update is on its own. Both are **rough subjective ratings**, just to illustrate how the tasks compare (Table 2).

**Table 2.** The five tasks. States is how many states a problem can be in. Both difficulty ratings are our rough judgments. CoT is partial if the completion may write the state on any line, and full if it writes it on every line.
{: .caption}

| task | states | tracking difficulty | step difficulty | CoT |
|---|---|---|---|---|
| *Cups*{:.task} | 5 | ●●● | ○○○ | partial |
| *Dataflow*{:.task} | 10⁸ | ●●● | ●●○ | partial |
| *Turtle*{:.task} | 400 | ●●○ | ●○○ | partial |
| *Calendar*{:.task} | 365 | ●○○ | ●○○ | partial |
| *Arithmetic*{:.task} | – | ○○○ | ●●○ | full |

The two extremes show the difference. A swap in *Cups*{:.task} only exchanges two cups, yet theory says no fixed-depth transformer can follow swaps of 5 cups at every length ([Barrington, 1989](https://doi.org/10.1016/0022-0000(89)90037-8); [Liu et al., 2023](https://arxiv.org/abs/2210.10749); [Merrill et al., 2024](https://arxiv.org/abs/2404.08819)), which is why T2MLR tests on it too. *Arithmetic*{:.task} writes its whole state on every line, so there is nothing to track, but each line computes a mod-100 sum or product and copies a long expression.

**Training.** Unless noted, every task starts from the pretrained d10 FBT (66/28/6), and the d10 GPT, trained the same way, is the baseline.

- **SFT** trains on short problems, 1 to 64 steps (1 to 8 operators for *Arithmetic*{:.task}), with 3 Jacobi passes.
- **RL** trains on longer ones, 33 to 128 steps (9 to 14 operators), with replay and $H = 2$, which sends the gradient 2 hops back but doesn't cap the chain the model uses. It is nanochat's REINFORCE, with 16 samples per prompt and each sample's advantage its reward minus the group's mean, like GRPO without the std normalization or KL penalty.
- Some RL runs add a **length penalty**, so a right completion of $n$ tokens earns $1 - 0.0005n$ instead of 1. Using the CoT then costs reward, which gives the model a reason to carry the state in the latents instead.

**How we measure.** We measure how the model uses its latents in four ways, mostly on its own completions and on CoTs with no states written. For the *Cups*{:.task} prompt of Figure 4, with one line of the CoT per column, they look like this:

```
own completion       34  25  25>2  23  15  35>5  =5
no states written    34  25  25    23  15  35    =?
no-CoT variant       =?
```

The model's own completion writes some states. With no states written, the model is fed a CoT that restates every swap but writes no cup, and has to name the last cup. The no-CoT variant of *Cups*{:.task}, which sections [4.4](#44-long-chains-reach-further-with-a-gradient-through-the-latents) and [4.5](#45-what-the-latents-carry-and-how) also use, is trained to answer right after the prompt.

- **No latents** is the accuracy with no latent fed anywhere, which is the plain transformer on the same weights. If it holds up, the task doesn't need the latents.
- **No states written** is the accuracy with a teacher-forced CoT that writes no state, as above. The state then has to come through the latents or be recomputed from the text. This measures what the latents can carry, which can be more than the model uses on its own completions.
- **Hops** is the length of the **effective chain**. A $K$-pass Jacobi forward lets information travel at most $K-1$ hops through the latents. We replay the model's own completions, or CoTs with no states written, with $K$ = 1, 2, 3, 4, 6, 8, 12, 16, 24, … passes. The fewest passes that reproduce their answers and written states as often as exact decoding does (within 0.03, McNemar p > 0.05) give the model's hops, $K-1$. If 16 passes match exact decoding but 12 don't, for example, the model needs 12 to 15 hops, and we report 15. Each hop count is an upper bound at the grid's resolution.
- **Probes** read the state from the latent, like a linear probe for the ball's cup on *Cups*{:.task}. LEACE ([Belrose et al., 2023](https://arxiv.org/abs/2306.03819)) erases a probe's code from every fed latent to test whether the model uses it, and swapping in another chat's latents tests whether the answer follows them.

## 4. Findings
### 4.1. FBT can learn a long chain

Can FBT learn a long chain, and how much SFT does it need? We take *Cups*{:.task} SFT checkpoints from 0.5M to 5.6M chats at d6, d8 and d10, and test each with no states written at 65 to 128 swaps. That is past SFT's training lengths and far past what one forward can track, so the cup has to travel through the latents (Figure 5).

![SFT checkpoints with no states written](/assets/img/fbt/sft_chain-light.svg){: .light w="603" h="330" }
![SFT checkpoints with no states written](/assets/img/fbt/sft_chain-dark.svg){: .dark w="603" h="330" }
_**Figure 5.** The chain appears abruptly after enough SFT. Cups SFT checkpoints at d6, d8 and d10, trained on 1 to 64 swaps and tested at 65 to 128 swaps with no states written. Hops are on the same chats, shown as 0 where accuracy is below 0.3._

- **The chain appears abruptly.** Below about 1M chats no size carries the cup, and RL from there never learns to ([section 4.2](#42-on-cups-only-a-length-penalty-puts-the-chain-to-use)). Smaller models need more SFT.
- **More SFT means fewer hops.** d10 carries the cup over 23 hops after 1.2M chats and 7 after 5.6M, so each hop covers more swaps. After pretraining the chain is about two hops ([section 1](#1-pretraining)).

*Turtle*{:.task} needs a lot of SFT too. With neither position nor direction written, d10 gets the answer right for about 8 moves after 2M chats, and through 33 to 64 moves after 4.6M (0.90, and 0.02 without latents), over 2 to 3 hops.

We train the chain with SFT, but it comes from the data, not the stage. Many *Cups*{:.task} chats leave long stretches of swaps unwritten, and we'd expect pretraining on them to build the same chain, though we haven't tested that. Not every task's data builds one. *Dataflow*{:.task}'s builds none, even after 7M chats ([section 4.3](#43-across-tasks-fbt-mostly-uses-the-cot-even-with-a-length-penalty)).

### 4.2. On *Cups*{:.task}, only a length penalty puts the chain to use

We continue each SFT checkpoint from [section 4.1](#41-fbt-can-learn-a-long-chain) for 300 steps on longer problems, 33 to 128 swaps, by RL with the length penalty, RL without it, or **more SFT** on about as many sequences (Figure 6).

![What each continuation does with the chain](/assets/img/fbt/use_chain-light.svg){: .light w="632" h="657" }
![What each continuation does with the chain](/assets/img/fbt/use_chain-dark.svg){: .dark w="632" h="657" }
_**Figure 6.** The latents can carry the cup after any continuation, but only RL with the length penalty leaves the cup to them, over about twice as many hops. Cups, d10, at 65 to 128 swaps. Gray: the SFT checkpoints of Figure 5. Colored: each continued for 300 steps on 33 to 128 swaps by more SFT at RL's learning rate, RL without the penalty, or RL with it. Top and bottom feed a CoT with no states written, and the middle uses the model's own samples at T = 1. Hops show as 0 where accuracy is below 0.3._

**The latents can carry the cup after any of the three.** From about 2M SFT chats, all three continuations get the cup right with no states written 0.85 to 1.00 of the time (Figure 6, top). Below about 1M chats, where SFT hasn't built the chain, none of them finds it.

**Only the length penalty makes the model use them.** Without the penalty, RL keeps writing half or more of the cups, as more SFT does (Figure 6, middle), and its samples lose almost nothing without their latents. With the penalty, it stops writing cups and carries the cup through runs of about 70 unwritten swaps, and without its latents it is at chance past 16 swaps (Figure 7). GPT under the same penalty drops cups only in runs of 4 to 5 swaps, about what one forward can track from the last written cup.

With the latents, both FBT runs are right 0.98 to 1.00 at every length._

**It does so only once the latents carry the cup almost perfectly.** Continued from the checkpoint after about 1M SFT chats, RL with the penalty gets only 0.22 with no states written, and its samples keep writing half the cups (Figure 6, middle). Skipping every cup saves about 200 tokens, worth 0.1 of reward, so it pays only if the model is right about 90% of the time with no states written. At d6 from 2M chats, RL raised that accuracy to 0.89, but its samples kept writing a third of the cups, and from 6M chats they wrote none.

**Using the chain lengthens it.** With the penalty, RL's chain takes about twice as many hops as that of the SFT it started from, while the other two continuations add few or none (Figure 6, bottom). The same holds at d6 and d8. From 5.6M SFT chats, RL with the penalty takes d10 and d8 from 7 hops to 15, and d6 from 7 to 23.

**Past training lengths, RL with the penalty does best.** Past 128 swaps, longer than any run trained on, it does best at every size, with 0.73 to 0.96 at d10 against 0.25 to 0.46 for the other two (Figure 8). At d6, RL without the penalty gets partway, to 0.52 to 0.68.

### 4.3. Across tasks, FBT mostly uses the CoT, even with a length penalty

FBT can get the state from one step to the next in two ways.

- **Use the CoT.** Write the state, or recompute it from the text within one forward, as a standard transformer does.
- **Use the latents.** A position's top state feeds the next position's first layer, and from there the state sits in the KV cache, where later positions read it. Each such hop gives the next update a fresh stack of layers, so a state that one forward can't rebuild from the text takes many hops in a row.

On *Cups*{:.task}, FBT uses the latents only under the length penalty, which makes each written state cost reward ([section 4.2](#42-on-cups-only-a-length-penalty-puts-the-chain-to-use)). Table 3 applies the same penalty to all five tasks, for FBT and GPT alike.

States written is the percentage of states the CoT writes out explicitly. No latents is FBT with no latent fed. Hops is the length of FBT's latent chain (section 3).

|---|---|---|---|---|---|---|
| *Cups*{:.task} | 2% | 60% | 0.98 | 0.16 | 0.97 | 23 |
| *Dataflow*{:.task} | 100% | 100% | 0.80 | 0.47 | 0.80 | 1 |
| *Turtle*{:.task} | 100% positions,<br>0% directions | 100% | 1.00 | 0.73 | 1.00 | 1 |

GPT is about as accurate on every task, so the latents never buy accuracy here. On *Cups*{:.task} and *Turtle*{:.task} they save tokens instead, with only as many hops as each task needs. *Turtle*{:.task}'s direction, which the text nearly gives away, takes one hop, and without the latents *Turtle*{:.task} drops from 1.00 to 0.73. Only *Cups*{:.task}, where nothing else tracks the cup, runs a long chain. *Calendar*{:.task}, *Dataflow*{:.task} and *Arithmetic*{:.task} write every state in the CoT and lean on one hop at most. 

A few caveats apply:
- **On *Calendar*{:.task} and *Dataflow*{:.task}, the penalty never got to act.** RL's sampling collapsed onto writing every state early on, before leaving a state out could pay. GPT's did the same on *Turtle*{:.task}, so *Turtle*{:.task} doesn't compare the two architectures.
- ***Dataflow*{:.task} is unsolved past 64 steps.** Its SFT never learns to carry a value, even after 7M chats, and RL reaches 0.80 by writing every value.
- **On *Arithmetic*{:.task}, the latents don't change accuracy.** Under the penalty it evaluates two operators in about a quarter of its lines, as GPT does, and those fit in one forward.

So even when writing costs, FBT keeps most of its states in the CoT, and its latents buy no accuracy over GPT.

### 4.4. Long chains reach further with a gradient through the latents

RL can send the gradient $H$ hops back through the latents ([section 2.2](#22-gradient-through-h-hops-from-one-forward)), and every RL run above uses $H = 2$. Setting $H > 0$ matters only where the model uses a long chain, which is perhaps what one would expect, since only a long chain has many hops for the gradient to follow back. Even there, it matters only past RL's training lengths.

The clearest case is a variant of *Cups*{:.task} with no CoT, which answers right after the swaps, so the cup can only travel through the latents. There $H$ = 0, 2 and 8 end within 0.04 of each other inside RL's lengths at d10, but past them $H = 2$ wins (Table 4).

### 4.5. What the latents carry, and how

*Cups*{:.task} carries the whole cup in the latent. With the length penalty, a probe reads the cup from the latent at 0.97 or better at every length through 128 swaps, on the model's own samples. With one pass, which feeds no latents, it reads the cup only at chance past 32 swaps. Replacing a completion's last 16 fed latents with those of a chat that starts one cup over moves 88 to 95% of its answers to that chat's cup.

The no-CoT variant from [section 4.4](#44-long-chains-reach-further-with-a-gradient-through-the-latents) shows the code most clearly (Figure 9). It is a linear code of at most 4 dimensions, which a probe reads at 0.98. Erasing it from every fed latent drops the model to chance, while erasing 4 random dimensions loses nothing, and steering the code in 8 consecutive latents moves every answer to the new path.

![Erasing and steering the cup code](/assets/img/fbt/probes-light.svg){: .light w="784" h="337" }
![Erasing and steering the cup code](/assets/img/fbt/probes-dark.svg){: .dark w="784" h="337" }
_**Figure 9.** The model uses a 4-dimensional linear code for the cup. The no-CoT variant of Cups, d10 after RL. Left: accuracy at 65 to 128 swaps with every fed latent removed, its code erased (LEACE), only its code kept, or 4 random dimensions erased. Right: the share of answers that switch to another path when w consecutive latents, from swap 16, get that path's code._

*Turtle*{:.task} carries only the direction. With no states written, a probe reads the direction from every latent at about 1.00, and erasing its 3-dimension code takes d10 from 0.91 to 0.30 at 33 to 64 moves (a random 3-dimension erasure costs nothing). No probe reads the position from any layer along the CoT. Instead, at the answer, `=` attends to every forward move, each holding its direction from the latent, and adds them up. That sum is what fails on long problems.

The latents carry only what the text doesn't give back easily. In *Cups*{:.task} that is the whole cup. In *Turtle*{:.task} it is the direction, never the position, which the model sums from the moves at the answer.

In both tasks, the state is rebuilt at each hop rather than passed along unchanged. The fed latent lands in a position's first few layers, which write the state into their keys and values, and later positions read it from there through attention. On *Turtle*{:.task}, the next position reads the direction from the values of layers 1 to 3 at the position before it. On *Cups*{:.task}, the answer reads the cup from the last 8 to 16 positions. About 1% of a fed latent's code is left by the top of the stack, so each position's last few layers work the state out again before handing it down.

What sets the number of hops is whether one forward can rebuild the state from the text. Under the length penalty, *Turtle*{:.task} writes every position, and the positions give the direction away within a few lines. Without latents the stack works the direction out by layer 4. The hop only gets it to the next position a couple of layers earlier, so nothing builds on it, and a 2-pass forward gives the same answers (0.98 against 1.00). *Cups*{:.task} is different. One forward tracks only about 20 swaps, so each position's new cup has to start from the one that came through the latent, and the hops stack up. Each hop is followed by a read across several positions, so 65 to 128 swaps, hundreds of positions, take only 15 to 31 hops.

[Appendix A](#appendix-a-explore-the-models) has the probes and tests for *Cups*{:.task} and *Turtle*{:.task}, for every model and size, in two interactive pages. One walks through single chats (Figure 10), and the other has the results over many chats (Figure 11).

## 5. Takeaways

We post-trained small FBTs on synthetic state-tracking tasks to see what the feedback adds over a standard transformer. FBT can learn a long latent chain, but whether it does depends on the task and the data. On *Cups*{:.task}, the chain appears abruptly after enough training, and RL can't find it without enough SFT first. Only RL with a length penalty extends it past its training lengths, more so with a gradient through more hops.

But FBT uses the chain only as a last resort. Without a length penalty, it keeps writing states in the CoT, as GPT does, even when its latents could carry them. With the penalty, it leaves out only what it can recover cheaply. On *Turtle*{:.task}, it stops writing the direction and passes it one hop through the latents. Only on *Cups*{:.task}, where nothing else can track the cup, does it use the long chain, and only once the chain gets the cup right about 90% of the time. GPT is about as accurate on every task, so the latents buy shorter completions, not accuracy.

We read these results as an upper bound on how much FBT relies on its latent chain. The tasks were picked to need serial state tracking, the training is very specific, and the length penalty rewards leaving state out. If FBT uses its chain only as a last resort here, we expect this preference for CoT over latent chaining to be stronger on more realistic tasks. (Not entirely surprising, we're using Transformers over RNNs for good reason.)

And RL on FBT itself is very practical. Save the fed latents while sampling, replay the rollout in one forward, and send the gradient a couple of hops back through the latents.

## Appendix B. Reproducing FBT Pretraining

The GPT baselines are a depth ladder from d6 to d14 (23M to 164M parameters), trained on ClimbMix at 100 tokens per parameter. Each FBT trains on its GPT base's tokens with the paper's 75/22/3 schedule, with 66/28/6, which spends more steps on feedback, or with two passes throughout (0/94/6, d6 to d10 only). Runs are single seeds, good to about ±0.4 × 10⁻³ bits per byte (bpb) of validation loss.

Our setup differs from the paper's in more than size. The paper's model has 1B parameters and uses mostly sliding-window attention over an 8192-token context, where ours use full attention over 2048 tokens. It trains on the Phi-4 mix of synthetic data and code, against our web text, with a 100k tokenizer to our 32k. We also didn't tune the pass schedule. The paper changes it with almost every token budget, and which one suits a given scale is an open question.

![Feedback gain against compute, ours and the paper's](/assets/img/fbt/pass_scaling-dark.svg){: .dark w="640" h="357" }
_**Figure 12.** The feedback's gain against training compute. Loss with 2 passes relative to 1 pass on the same model, where below 0 the feedback helps. Ours are d6 to d14 under three pass schedules (the share of steps at 1, 2 and 3 passes). The paper's are its 1B model at four token budgets (its Fig. 5), at estimated compute._

**We couldn't fully reproduce the paper's feedback gain at our scale** (Figure 12). With the paper's 75/22/3 the second pass never beats the plain pass, though it trails by less with scale, down to 0.01% of the loss at d14. In the paper the second pass cuts the loss by about 1% at every budget. Any of the differences above could matter, and we haven't tested which.

We still consider this a faithful reproduction. FBT's plain pass trails GPT by 0.03% to 0.17% of the loss, against 0.10% to 0.30% in the paper, and the feedback gain moves the paper's way with scale. With 66/28/6, which spends more steps on feedback, the second pass beats the plain pass from d10 up, by 0.05% at d14. Two passes throughout gains more, up to 0.23%, but costs 2.07× GPT's FLOPs and never settled at d8. So every model we fine-tune is pretrained with 66/28/6.

**Given the same FLOPs and data, GPT still wins** (Figure 13). FBT spends 28% to 107% more FLOPs than GPT on the same tokens. Its pitch is data efficiency, so the fair baseline is GPT trained for the same FLOPs on the same data, repeating its tokens for 1.28 to 2.07 epochs.

## Appendix C. Deriving the gradient trick

This derives the gradient trick of [section 2.2](#22-gradient-through-h-hops-from-one-forward). Write the replay forward as $h = F_\theta(z)$, with the tokens implicit. In the real recurrence $z = S h$, so the total derivative of the states is

$$
\frac{dh}{d\theta} = \frac{\partial F}{\partial \theta} + A\, \frac{dh}{d\theta}, \qquad A = \frac{\partial F}{\partial z}\, S,
$$

which solves to

$$
\frac{dh}{d\theta} = (I - A)^{-1} \frac{\partial F}{\partial \theta} = \sum_{j=0}^{T-1} A^j\, \frac{\partial F}{\partial \theta}.
$$

$A$ maps a change in one position's state to the change it causes one hop later. It is nilpotent, since a position only depends on earlier latents, so the series is finite, and its $j$-th term is the gradient through exactly $j$ hops of latent feedback. The pinned passes truncate it at $H$ hops:

$$
\nabla_\theta \mathcal{L} \approx \Big(\sum_{j=0}^{H} (A^\top)^j g\Big)^{\top} \frac{\partial F}{\partial \theta}, \qquad g = \frac{\partial \mathcal{L}}{\partial h}.
$$

Each application of $A^\top$ is a backward from the states to the fed latents alone, through the graph of the one forward, followed by a shift back one position. The weights then need a single full backward, with the summed gradient, as in the code in section 2.2.

With $H \ge T-1$ the result is the exact gradient of the recurrence. Literal pinned passes would then store $T$ steps' worth of activations, and the gradient trick still one. We checked the exact case against $T$ literal Jacobi passes on the exact latents, and smaller $H$ against literal pinned passes.
